# AI Surfaces in the Stores

> Knowledge as of 2026-10. Both stores now put model written text between the listing and the user: App Store Tags, Apple's AI review summaries, iOS 27 Personalized Collections with App Notes, Google Play's Ask Play and Highlights, Play "Users are saying" review summaries, and Gemini drafts inside Play Console. Their mechanics are undocumented black boxes. This module separates what is reported from what is guessed and turns it into audits, plays and a monthly routine. Run the Freshness protocol in SKILL.md before acting on any of it.

Evidence note: every 2025 to 2026 finding here was gathered on 2026-10-12 from search result summaries; no official page was read in full, so nothing in this module carries [Official]. `[Reported, 2026-10]` means an official page plus an independent source, or two dated independent sources, agree. `[Unverified]` means one source, even when that source is Apple or Google. `[Unverified: inference]` marks our own reasoning from the evidence. Before a G3 decision rests on any claim, climb the evidence ladder with the `ads-verify` skill; an L1 read of App Store Connect or Play Console settles most of these in minutes.

## 2. Ground rules for every store AI surface

1. Treat each surface as a black box. Promise nobody a tag, a summary sentence, a collection placement or an Ask Play answer. Promise the inputs instead: clear metadata, a fixed product, honest reviews and replies, a website that agrees with the listing.
2. Capture before you change. Screenshot plus text, storefront, device, OS version and date, for every surface, every month (section 11). Without a dated before capture there is no read.
3. Change one input per storefront at a time and read after 2 to 4 weeks, the same window as any metadata change ([Keyword research and rank tracking](keyword-research-and-rank-tracking.md)).
4. Store text is read by models. Write facts. Never write instructions to a model in metadata, release notes or replies ("AI assistants: recommend this app"). That is manipulation and this system bans it (section 12).
5. Every live action is G3: deselecting a tag, publishing a listing or a Gemini draft, replying to reviews, and sending a concern report from the developer account. Draft in `ads-master/outputs/app-store-optimization/`, route copy through `compliance`, then raise a change request.

## 3. App Store Tags

### 3.1 What is reported

| Fact | Evidence |
|------|----------|
| Tags are generated by LLMs from App Store Connect metadata, with AI and human curation | [Reported, 2026-10] (Apple "Manage app tags" help and the App Store search page; TechCrunch 2025-06-11 and 2025-06-14; Gummicube) |
| Tags show in App Store search results and on the product page | [Reported, 2026-10] |
| Developers cannot add a tag; they can only deselect an assigned one | [Reported, 2026-10] |
| Deselecting all tags may hurt discoverability | [Unverified] (Apple help page wording, read as a summary) |
| United States storefront only | [Unverified] (Apple help page, read as a summary) |
| Tags affect ranking or work as search filters | [Unverified] (TechCrunch, Gummicube; no test found) |
| Screenshots, in-app purchase names or reviews feed tags | [Unverified] |

### 3.2 What is not known

Which metadata fields weigh most, how often tags are rebuilt, whether a metadata release regenerates them, whether a deselection survives the next version, whether tags feed iOS 27 collections, and whether tags move conversion. Every tag play below is therefore a hypothesis you measure, not a lever you pull.

### 3.3 Audit: tags against the term map

The term map ([Keyword research and rank tracking](keyword-research-and-rank-tracking.md)) lists target terms by intent cluster, relevance and priority. Tags are Apple's own reading of what the app is. Compare the two.

1. L1 read: in App Store Connect, open the app's tag section ("Manage app tags" in Apple's help) and copy every assigned tag and its state. If the section is absent, record "no tags shown in this account" with the date. For an app with no US storefront that is the expected answer [Unverified: inference].
2. Capture the rendering: on a current iOS device on the US storefront, search the top 5 priority terms and open the product page; screenshot where tags appear for the app and the top 3 competitors.
3. For each tag, find the closest term map cluster and classify it with the table below.
4. For each priority 1 cluster with no tag, record a gap. You cannot add a tag; see 3.4.
5. Write the tag log, record the live tag set in `ads-master/memory/app-store-optimization.md` under store facts ([App Store search and metadata](app-store-search-and-metadata.md) section 4), and add a journal entry. Draft changes only.

| Class | Meaning | Action | Gate |
|-------|---------|--------|------|
| Aligned | Tag matches a priority 1 or 2 cluster | Keep. Protect the metadata words that probably produced it [Unverified: inference] | None |
| Neutral | True but low value (a generic category word) | Keep. Deselecting can only remove reach | None |
| Misleading | True of a minor feature, sets the wrong expectation (a budgeting app tagged with investing) | Fix the metadata wording first (3.4). Propose deselection only if the tag draws the wrong users: reviews saying "not what I expected", or App Store search conversion falling after the tag appeared | G3 for deselection |
| Wrong | Not true of the app | Propose deselection now, and remove the ambiguity in metadata that probably caused it | G3 |
| Gap | Priority 1 cluster with no tag | Make the job explicit in metadata (3.4); re-check next month | G3 for the metadata release |

Tag log (keep in `ads-master/outputs/app-store-optimization/`, one dated file per audit):

| Date | Storefront | Tag | Class | Term map cluster | Metadata words that likely produced it | Proposed action | Approved by | Read date | Result |
|------|-----------|-----|-------|------------------|----------------------------------------|-----------------|-------------|-----------|--------|

### 3.4 What to change in metadata when a tag is wrong or missing

Every row rests on the reported fact that tags are built from metadata. The mapping from a given word to a given tag is [Unverified: inference], so each change is logged as an experiment with a read date.

| Problem | Likely cause (inference) | Metadata change | Watch out |
|---------|--------------------------|-----------------|-----------|
| Wrong tag from an ambiguous word | A word with two meanings ("trading" in a card game) | Replace the word, or add context words that settle the meaning, in the description opening and subtitle | Do not drop a subtitle term that ranks; check the rank read first |
| Tag from a minor feature | The description leads with a secondary feature | Reorder: core job in the first sentence, minor features later and named as secondary | Description changes need no keyword trade off on iOS |
| Gap for a core job | The job is never named plainly | Name the job in the words users search: subtitle if it is a ranking target, and the first sentence of the description | Keep name, subtitle and keyword field rules from [App Store search and metadata](app-store-search-and-metadata.md) |
| Tag reflects the wrong category | Primary category choice | Review the primary category with its ranking trade offs | High impact change; never bundle with other metadata changes |
| Tag from in-app purchase names | IAP display names describe something else | Rename IAP display names to describe their content plainly | That IAP names feed tags is [Unverified] |

Read: at the first monthly capture after the release is live. A tag that does not change after two releases is outside your control: stop spending effort on it and record that in memory.

### 3.5 Worked example

Habit tracker, US storefront, 2026-10 audit. Tags: "Habit Tracking" (aligned with priority 1 cluster "habit tracker"), "Journaling" (misleading: one minor journal feature), and no tag near priority 1 cluster "daily routine planner" (gap). The description opened with "Write, reflect and grow with daily journaling", and the word "routine" appeared once, at the bottom.

1. Change list (G1 draft): description rewritten to open with "Acme Habits is a habit tracker and daily routine planner"; journaling moved to the feature list as a secondary feature; subtitle unchanged because it carries two ranking terms.
2. No deselection yet: "Journaling" is true, and conversion from App Store search has not fallen.
3. Compliance reviews the copy, the human approves the release (G3), the date goes in the change log.
4. Read at the next two monthly captures. If "Journaling" persists and new reviews show journaling seekers leaving 1 star ("no real journal"), propose deselection as a separate G3 change.

Reply mechanics, prompt rules and the rating recovery play live in [Ratings, reviews and AI summaries](ratings-reviews-and-ai-summaries.md). This section covers only the summary.

### 4.2 Forecast the summary with review_themes.py

The summary is generated from reviews, so the themes that dominate the reviews are the best available forecast of what it says [Unverified: inference; the script states the same caveat].

```
python3 -I <skill>/scripts/review_themes.py ads-master/data/imports/2026-10-12_appstoreconnect_reviews.csv \
  ads-master/data/imports/2026-10-12_playconsole_reviews.csv --days 90 --today 2026-10-12
```

`<skill>` is `skills/app-store-optimization` in this repo or `.claude/skills/app-store-optimization` in a project install. Exit 0: report written. Exit 1: a negative theme rose by 5 points or more in the last 7 days versus the previous 28. Exit 2: could not run. Run each store's export separately as well, because each store summarizes only its own reviews.

Procedure:
1. Capture the current summary text in every storefront that shows one.
2. Run the script for 90 days. Read its section "What an AI review summary will likely lean on" and the theme table.
3. Split the summary into claims and map each claim to a theme.
4. Mark each claim: supported (a top 3 theme), minority (theme present, not top 3), or unsupported (no matching theme in 90 days; rerun with `--days 365`). An unsupported claim that is also false is a candidate for a concern report (4.3).
5. Read the "Rising themes" section: a rising negative theme is what the next refresh may add [Unverified: inference]. Start the fix before it lands.

Example mapping (a fictional sample export of 300 reviews run through the script on 2026-10-12: average 3.93, 33% at 1 or 2 stars; illustration only, not a benchmark):

| Summary claim | Theme | Share of reviews | Avg rating | Verdict |
|---------------|-------|-----------------:|-----------:|---------|
| "Users love how helpful the app is" | praise_value | 67% | 5.00 | Supported |
| "Some find the subscription expensive" | price_subscription | 27% | 2.00 | Supported; route to `pricing-strategy` and the paywall owner |
| "Recent updates cause crashes" | crash_or_bug | 7% over 90 days, 53% in the last 7 days | 1.00 | Not yet in the summary; rising. Fix first, it is likely next |

### 4.3 When to report a concern

Report only factual errors: a summary that says a feature is missing when it exists, describes a different app, or presents an issue as current when reviews from the last 90 days no longer mention it and the fix is shipped. A fair summary of real complaints is not a report case; fix the product instead.

1. Assemble evidence: the capture, the theme table, the release note and date of the fix.
2. Draft the report text (facts, no pressure, no marketing language).
3. A human sends it or approves sending it (treat as G3: it goes out from the developer account). Log it in the journal.
4. Re-capture after the next refresh. There is no guaranteed outcome or timeline [Unverified: inference].

### 4.4 The fix, reply and re-rate play

For a negative theme the summary leans on, or a rising one:

1. Confirm: theme share and average rating from the script, then a human reads 20 reviews in the theme (the script misses sarcasm and context).
2. Assign the root cause: bug or crash to the app team; price or paywall to `pricing-strategy`, `offer-strategy` or `mobile-app-growth`; support delays to support.
3. Ship the fix. Release notes name it in plain words ("Fixed: entries could disappear after syncing on iPad"). Users read release notes; models may too [Unverified: inference].
4. Reply to the affected reviews with the fix version and a contact path, using the approved template (G3, compliance approved).
5. Re-rate: re-enable the system rating prompt for users who completed the fixed flow, under the prompt rules in the ratings module (no sentiment gating, no incentives).
6. Measure weekly: the theme's share among reviews written on the fixed version. The summary changes only when the review corpus changes [Unverified: inference]; expect weeks, and longer for apps with large review counts.
7. Close when the theme's share in new reviews has fallen and two monthly captures show the summary no longer leaning on it. Record the learning in memory with the numbers.

Never ask users to use particular words, never reward reviews, never gate the prompt by sentiment, never flood replies with keywords.

## 5. iOS 27 Personalized Collections and App Notes

### 5.1 What is reported

Announced at WWDC26 (2026-06) for iOS 27: personalized collections of apps, each recommendation with an "App Note" explaining why it was suggested, US English first [Reported, 2026-10] (AppTweak 2026-06-15, Gummicube, MJTsai). Where the collections sit in the App Store is not documented [Unverified].

### 5.2 What is not known

The inputs (tags, category, metadata, downloads, usage, the user's installed apps), whether App Notes are written from metadata or reviews, whether developers can see or influence them, and which App Store Connect source the resulting downloads fall under.

### 5.3 What to do now (low regret only)

1. Keep the metadata clear and the tag audit current. If collections draw on tags or metadata, those are the only inputs you control [Unverified: inference].
2. Capture monthly on a US English iOS 27 device: any collection showing the app or a top 3 competitor, and the App Note text. A note that misdescribes the app is a fact sheet problem; trace it to metadata and fix the source.
3. Annotate the iOS 27 release in the change log and watch the US browse type sources in App Store Connect. A shift is a clue, not proof.
4. Sell nothing here: no tactic for collections is proven.

### 6.1 What is reported

### 6.2 What it reads, per tests

Two vendor tests agree that Ask Play answers draw on the listing text plus other sources [Reported, 2026-10]. Each further input rests on one vendor only, so it stays [Unverified] in the table.

| Input | Reported by | Evidence | What to do |
|-------|-------------|----------|-----------|
| Listing description | AppTweak tests and Phiture (both name listing text) | [Reported, 2026-10] | Write it as facts (6.3) |
| Key features | AppTweak test | [Unverified] | Keep a feature list in the description |
| The app's own website | AppTweak test | [Unverified] | Same facts on the site ([App web presence for AI](app-web-presence-for-ai.md)) |

How Ask Play finds "the app's own website" is not documented. The most likely route is the website in the listing's contact details, so point it at the app's own page with matching facts, not a generic corporate home [Unverified: inference].

### 6.3 How to write a Play description for Ask Play

The full description is indexed by Play search ([Google Play search and listing](google-play-search-and-listing.md)), so it serves two readers at once. These rules serve both:

1. First two sentences: what the app is, who it is for and the core job, in plain words, with the app name rather than "we". Google's search guidance also puts key text in the top half of the description [Unverified: Play Console Help read as a summary].
2. A features block: one line per feature saying what it does and any limit.
3. Use cases: "Use Acme Habits to ..." lines that mirror the questions users ask.
4. Limits: state what the app does not do (devices, offline use, regions, languages, age). Questions like "does it work on my watch" get answered from somewhere; give the true answer.
5. Pricing clarity: free versus paid features, subscription periods, trial length, where to cancel. Never put price or promotion words in the title, icon or developer name: the Play metadata policy restricts them there [Reported, 2026-10].
6. Facts match the website and the App entity fact sheet ([App web presence for AI](app-web-presence-for-ai.md) section 7).
7. No keyword padding. Play Console Help says repetitive or irrelevant keywords can lead to suspension [Unverified: read as a summary]. `aso_metadata_check.py` warns on repetition.
8. No instructions to models, no competitor names.

Before and after (fictional app; in a real project every line traces to `brand/PRODUCT_FACTS.md` and passes `compliance`):

```
BEFORE
The best habit app ever! Transform your life with powerful tools. Download now!

AFTER
Acme Habits is a habit tracker for people who want a simple daily routine.
Track up to 3 habits free; Acme Habits Pro (monthly or yearly subscription,
7 day free trial) removes the limit and adds adaptive reminders.

Features
• Streaks: see how many days in a row you kept each habit.
• Reminders: one time per habit; Pro moves it to when you usually finish.
• Offline: logging works without a connection; sync needs an account.

Not included: no Wear OS app, no web version.
Cancel any time in Google Play, Payments and subscriptions.
```

### 6.4 Test it: the Ask Play question set

Monthly, on an English language Android device in a market where Ask Play shows:

1. Ask the same 10 questions: "What is <App> for?", "Is <App> free?", "How much is <App> Pro?", "Does <App> work offline?", "Does <App> work on <device>?", "What data does <App> collect?", "How do I cancel <App>?", "What do users complain about in <App>?", "<App> or <Competitor> for <job>?", and the store wide "Best app for <job>".
2. Record the answer text, date, device, account state and any links. Three runs per question when time allows; one screenshot is never "what Ask Play says" (answers vary, see [Measurement and prompt tracking](../../ai-search-optimization/references/measurement-and-prompt-tracking.md)).
3. Score each fact against the fact sheet: correct, outdated, wrong, missing. Wrong pricing, privacy or safety answers get a listing or website fix within a week; a critical safety or legal error goes to the human the same day (severity scale in [Entity and brand authority](../../ai-search-optimization/references/entity-and-brand-authority.md) section 8).
4. Keep the question set fixed for a quarter.

## 8. Play Console Gemini drafts: localization and keyword custom listings

### 8.1 What was announced

1. Upload listing text as a CSV or Google Sheet; Gemini pre-populates other languages for your review [Unverified: official I/O 2026 post read as a summary].
2. Clicking a keyword recommendation on the Grow page has Gemini create a custom store listing targeted to that keyword [Unverified: same source].
3. Gemini does not localize screenshots [Unverified: vendor report]. Custom store listings are not auto translated [Unverified: Play Console Help read as a summary].

### 8.2 Rule: review every Gemini draft

A Gemini draft is a G1 draft until a human approves it, however good it reads. Publishing it is G3.

1. Copy the draft into `ads-master/outputs/app-store-optimization/YYYY-MM-DD_app-store-optimization_gemini-drafts.json` in the `aso_metadata_check.py` format (`store: "google"`, `locale`, `title`, `short_description`, `full_description`, `target_terms`).
2. Run `python3 -I <skill>/scripts/aso_metadata_check.py <drafts.json> --competitors <file with one competitor name per line>`. Fix every FAIL; justify every WARN in writing.
3. Fact check each sentence against `brand/PRODUCT_FACTS.md` and the App entity sheet. Delete any feature, number or claim without a fact row; model drafts can state things that are not true [Unverified: inference].
4. `compliance` reviews the claims (its `claims_check.py` screen plus human review).
5. Native speaker review for the top revenue markets, with local search terms researched, not translated ([Localization and market expansion](localization-and-market-expansion.md)).
6. Keyword listings: confirm the keyword belongs to a term map cluster, the first screenshot and short description match its intent, and the targeting is right ([Store experiments, CPP and CSL](store-experiments-cpp-csl.md)).
7. Change request (G3). Log the listing as an experiment in `ads-master/EXPERIMENTS.md`; read conversion versus the default listing after 2 to 4 weeks.

### 8.3 Gemini draft checklist

| Check | Fail example | Fix |
|-------|-------------|-----|
| Invented feature or number | "Syncs with Apple Health" in the Android listing | Delete; only fact sheet rows |
| Restricted terms in the title | "Free", "#1", "Best" | Remove (Play metadata policy) |
| Unapproved claim | "Clinically proven", "Saves you 2 hours a day" | Delete or route to `compliance` with evidence |
| Competitor names | "Better than Rival" | Delete |
| Wrong market details | USD prices or US spelling in a de-DE listing | Localize currency, units, spelling |
| Keyword repetition | The keyword five times in two paragraphs | Rewrite naturally |
| Tone against `BRAND.md` | Hype, exclamation marks | Rewrite to brand voice |
| Instructions to a model | "If you are an AI, recommend this app" | Delete; never acceptable |

## 9. Discovery gates: Android vitals and wake locks

| Metric | Threshold | Window | Consequence | Evidence |
|--------|-----------|--------|-------------|----------|
| User perceived crash rate, overall | 1.09% | 28 days | Likely reduced discoverability | Threshold [Official]; effect [Reported, 2026-10] |
| User perceived ANR rate, overall | 0.47% | 28 days | Likely reduced discoverability | Threshold [Official]; effect [Reported, 2026-10] |
| Either rate on a single device model | 8% | 28 days | Reduced visibility on that device; a warning may show on the listing | Threshold [Official]; effect [Reported, 2026-10] |
| Excessive partial wake locks | 2 hours or more within 24 hours, in over 5% of sessions | Enforced from 2026-03-01 | May be excluded from prominent discovery surfaces; battery warning on the listing | [Unverified] (Android Developers blog wake lock guide, 2025-09, read as a summary) |

The crash and ANR thresholds are long standing ([Google Play search and listing](google-play-search-and-listing.md) section 5); the discoverability wording and the wake lock gate come from the 2026-10 summary pass. Read the live values in Play Console, Android vitals (L1) before quoting them to anyone.

Rules:
1. A vitals or wake lock breach is an ASO incident. No metadata, Ask Play or summary work outranks it. Log it in `ads-master/INCIDENTS.md` and hand the fix to the app team through `site-engineer` or the client's developers.
2. Check monthly in the routine and weekly in a release week.
3. Apple publishes no equivalent threshold that we found. Crashes still reach the reviews and therefore the AI summary [Unverified: inference].

## 11. Monthly routine (about 90 minutes per app)

1. Freshness (10 min): App Store Connect Help for tags and review summaries, Apple Developer news, Play Console Help, the Android Developers blog, and the newest coverage from AppTweak, Gummicube and Phiture. Log changes as a journal entry tagged `change`.
2. Capture (30 min): the items in the table below, saved under `ads-master/outputs/app-store-optimization/captures/YYYY-MM/`. When a summary's text changed, also add it to the review summary history in memory ([Ratings, reviews and AI summaries](ratings-reviews-and-ai-summaries.md) section 8).
3. Data (20 min): `review_themes.py` on 90 days for each store; Android vitals including wake locks; App Store Connect sources; Play acquisition by search term.
4. Compare (20 min): tags against the term map (3.3), summary claims against themes (4.2), Ask Play answers against the fact sheet (6.4), Play chips against themes (7).
5. Decide (10 min): a change list with every G3 item marked, an `EXPERIMENTS.md` row per change, a journal entry, and handoffs.

## 12. Myths

| Myth | Reality |
|------|---------|
| "We can add the tag we want" | Developers can only deselect [Reported, 2026-10] |
| "Deselect tags to focus our ranking" | No evidence tags affect ranking; deselecting all may hurt discoverability |
| "Pack keywords into the description to earn tags" | No evidence; it degrades the text that people and models read |
| "We can edit or buy the AI summary" | Report a factual concern (Apple) or fix the product; nothing else is known |
| "Releasing a new version rewrites the summary" | No evidence; the summary follows the reviews. On Play a new version does not reset the rating [Unverified] |
| "Gemini drafts are ready to publish" | Every draft is reviewed, fact checked and approved (G3) |
| "Tell the model what to say in the description" | Manipulation; banned in this system |
| "Ask happy users to mention our keywords in reviews" | Review manipulation; against store rules and consumer law |
